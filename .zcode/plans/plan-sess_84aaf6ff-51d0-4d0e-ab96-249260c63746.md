# Fix Plan: Auto-Bond & Discovery for New DMG Users

## Root Cause Analysis

### Root Cause #1: Sponsor friend `bond.request` never reaches Allen

The new DMG user's sponsor loop calls `sendHello()` which builds dial hints (count=1 — the synthetic circuit hint via cn-relay). But `deliverCallEnvelopeViaRuntime()` at `node-service-outbound-messaging.ts:596-617` merges `listenAddrs` (from bundled sponsor friend config, which contains Allen's **private LAN IPs** `192.168.3.85:64589`) with `dialHints`, sorts circuit hints **last**, and dials each address sequentially. The LAN dial at `192.168.3.85:64589` fails with `ECONNREFUSED` (Allen is on a different network — his external IP is `106.37.113.92`). The circuit dial should then be attempted, but the `mesh.dial(addr)` call at line 612 catches and **silently swallows** the error. The code then falls through to `deliverCallEnvelopeWithRetry()` which calls `prepareOutboundPeerConnection()` → `ensurePeerReachable()` — but this also uses the **listenAddrs** which are still the private LAN IPs. All attempts fail. No `[send] attempt` error log is produced for Allen's peer ID because the failure happens in the `mesh.dial()` pre-dial phase, not in `mesh.send()`.

**Evidence from new user log:**
- `sendHello dialHints count=1` — 1 circuit hint exists
- `connected:false, direct:false, hintCount:1` — confirms no connection
- `ensurePeerReachable failed for /ip4/192.168.3.85/tcp/64…: connection error 192.168.3.85:64589: connect ECONNREFUSED` — all attempts hit private LAN
- **Zero** `ensurePeerReachable` or `[send] attempt` logs for Allen's peer ID through the circuit
- No "Hello sent successfully" log — `sendHello` throws before reaching line 155
- Relay log shows INBOUND STREAM from new user — but this is the new user's bond-warm to the relay, not the bond.request to Allen

**The fix:** When constructing dial targets in `deliverCallEnvelopeViaRuntime`, circuit hints for the sponsor peer ID should be tried FIRST (or at least should not be blocked by LAN attempts). The `listenAddrs` from the bundled config contain private LAN addresses that are unreachable — these should not prevent the circuit hint from being dialed.

### Root Cause #2: `handleBondIntentViaRuntime` missing bond autonomy callback (Tauri path bug)

`node-service-handlers-bond-intent.ts:63-106` calls `handleInboundBondIntent()` with only 3 arguments. The 4th argument `tryBondAutonomyAutoAccept` is never supplied. This means bond autonomy auto-accept is completely broken on the `wireMeshEventsViaRuntime` path (Tauri/mobile/embedded).

**However**, this does NOT affect the current scenario because Allen (the sponsor who needs to auto-accept) runs from CLI `npm run node:dev` which uses the `index.ts` direct handler (with all 4 arguments). But this is a latent bug that must be fixed for when the Tauri app is used as a sponsor node.

### Root Cause #3: `searchPeers` "Node not initialized" timing

The sponsor loop calls `searchPeers({ peerId })` at line 621 BEFORE `sendHello`. But `searchPeers` returns early with "Node not initialized" if the mesh hasn't been set on the NodeService. The `probeMeshReady` check at line 605-609 only checks mesh readiness (listen addrs + peers), not whether `searchPeers` is ready. The search failure itself is non-fatal — the loop continues to `sendHello`. But the error message is misleading and the DHT search would help establish the peer record.

### Root Cause #4: Inbound guard silent rejection

`node-service-wire-mesh-events.ts:117` — `if (guardDecision.action === "reject") return;` — no log, no audit event. If a message is rejected by the inbound guard (size, replay, signature), it silently vanishes. This makes debugging impossible.

## Fix Plan (6 Changes)

### Fix 1: `deliverCallEnvelopeViaRuntime` — circuit hints must not be blocked by unreachable LAN addresses
**File:** `apps/node/src/node-service-outbound-messaging.ts`, lines 596-618

**Problem:** The code merges `listenAddrs` (bundled LAN addresses) with `dialHints` (circuit hint), sorts LAN first and circuit last, dials each, but if the LAN dial hangs/fails, the circuit dial is attempted last. However, `mesh.dial(addr)` catches the error silently (line 615-617), and `conn.connected` stays false. The code then falls through to `deliverCallEnvelopeWithRetry` which ALSO dials using the merged hints.

**Fix:**
1. In the `deliverCallEnvelopeViaRuntime` pre-dial loop (lines 596-618), after all dials fail, add a diagnostic log showing what was attempted and what failed — don't silently swallow.
2. When `conn.connected` stays false after the loop AND there are circuit hints, ensure those circuit hints are passed to `deliverCallEnvelopeWithRetry` (they already are via line 656, but confirm `preferCircuitHints` is set to `true`).
3. In the sort at lines 601-608, when `preferCircuitHints` is true, sort circuits FIRST (not last). Currently circuit hints get `aCircuit=1` which sorts AFTER `aCircuit=0` (non-circuit). When circuits are preferred, they should come first.

### Fix 2: Wire `tryBondAutonomyAutoAccept` into `handleBondIntentViaRuntime`
**File:** `apps/node/src/node-service-handlers-bond-intent.ts` (line 63-106)
**File:** `apps/node/src/node-service-contexts.ts` (add to `BondHandlerContext`)
**File:** `apps/node/src/node-service-impl-service-deps.ts` (wire the callback)
**File:** `apps/node/src/node-service-impl.ts` (implement the callback)

**Changes:**
1. Add `tryBondAutonomyAutoAccept?: (...) => Promise<...>` to `BondHandlerContext` interface
2. Add corresponding field to `BondHandlerContextDeps` and `buildBondHandlerContext`
3. In `handleBondIntentViaRuntime`, pass `ctx.tryBondAutonomyAutoAccept` as the 4th arg to `handleInboundBondIntent` (line 105 — between the 3rd arg closing paren and the semicolon)
4. Wire the callback in `node-service-impl-service-deps.ts` to invoke `tryBondAutonomyInboundAutoAccept` with the same deps as the CLI path (config store, daily counter, intro correlation, trust overlap)
5. Store the bond autonomy daily counter as a private field on `NodeServiceImpl` (like the CLI does with `bondAutonomyDailyCounter`)

### Fix 3: Add diagnostic logging to silent catch sites
**Files:** Multiple

1. **`node-service-wire-mesh-events.ts:117`** — When guard rejects, add: `console.warn(\`[inbound-guard] REJECTED envelope intent=${envelope.intent} from ${remotePeerId}: ${guardDecision.reason}\`)`
2. **`node-service-outbound-messaging.ts:615-617`** — In the catch block, add: `console.debug(\`[deliver] mesh.dial failed for ${addr.slice(0,60)}…: ${err.message}\`)`
3. **`node-service-setup-sponsor-friend.ts`** — In `runSetupSponsorFriendRetryLoop`, the `sendHello` call at line 624 already logs dialHints count, but the error from `sendHello` is caught by the outer try/catch at line 597. Add a specific log: `console.warn(\`[setupSponsorFriend] sendHello failed on attempt ${attempt}: ${err.message}\`)` before re-throwing.

### Fix 4: Fix `searchPeers` timing in sponsor loop
**File:** `apps/node/src/node-service-setup-sponsor-friend.ts`, line 620-622

The `searchPeers` call happens before `sendHello`. If the mesh is initialized but searchPeers returns "Node not initialized", it means the internal `_mesh` field isn't set yet. Since the `probeMeshReady` check at line 605 already gates on mesh readiness, the searchPeers failure is a timing gap between `bindExternalMesh` (which the CLI calls at line 2629) and when `startNode()` fully initializes the internal `_mesh` reference.

**Fix:** Wrap the `searchPeers` call in a try/catch (it already doesn't throw, just returns []). But more importantly, ensure `probeMeshReady` checks for the `_mesh` field being set, not just libp2p being started. Alternatively, move the `searchPeers` call to AFTER the first successful `sendHello` (since the search is just for caching — the actual bond doesn't need it).

### Fix 5: Ensure `probeMeshReady` checks relay reservation availability
**File:** `apps/node/src/node-service-impl.ts`, `probeMeshReady` (line ~4875-4900)

**Current check:** mesh exists, has listen addrs, has relay reservation OR connected peers.

**Problem:** The new user node shows `circuitPeers=0 circuitConns=0` at uptime=60s when the first sendHello fires. The relay reservation is made AFTER the sponsor loop starts (the reservation log appears later). The `probeMeshReady` guard passes because `connected peers` is non-zero (161 DHT bootstrap peers connected), but the **relay circuit** to Allen isn't ready yet.

**Fix:** Add a relay-reservation-specific check to `probeMeshReady` — verify that at least one of the configured relay peers has an active reservation. Or add a delay/retry for the relay warmup to complete before the sponsor loop starts.

### Fix 6: Fix discovery — DHT provideSelf timeout
**File:** `apps/node/src/node-service-discovery.ts`

The log shows: `provideSelf: broadcast put timed out after 15s — DHT likely has no reachable peers`. This means the DHT bootstrap is failing even though 161 peers are connected. Those peers are libp2p public bootstrap nodes that don't support DHT content routing.

**Fix:** This is a DHT bootstrap configuration issue, not a code bug. The user's `bootstrapPresets` should include peers that support DHT. The existing presets (`public-libp2p`, `cn-relay`) may not all support KadDHT. This needs investigation but is secondary to the auto-bond fix.

## Implementation Order

1. **Fix 1** — Circuit dial priority (unblocks auto-bond delivery)
2. **Fix 3** — Diagnostic logging (makes future debugging possible)
3. **Fix 5** — probeMeshReady relay check (ensures circuit is ready before sendHello)
4. **Fix 4** — searchPeers timing (cosmetic, non-blocking)
5. **Fix 2** — Bond autonomy wiring (latent bug, important for Tauri sponsors)
6. **Fix 6** — DHT discovery (secondary, needs bootstrap peer investigation)
7. **Rebuild** DMG and test end-to-end
