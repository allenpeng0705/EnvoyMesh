## Issue 1 (P0): Allen CPU Spin — Relay Manager Snapshot Reads 122MB Audit Log

### Root Cause
`runRelayManagerSnapshotCycle()` at `apps/node/src/index.ts:4522-4523` calls `taskStore.readAuditEvents()` which calls `readJsonLines()` — this **reads the entire 122MB `audit-events.jsonl` into memory, splits by newline, and JSON.parses every line**. It then filters the full array looking for the last 12 relay traces.

This runs:
- **Once at startup** (line 3595) — blocks mesh initialization for 10-50s
- **Every 30 seconds** (line 4210-4221, `scheduleRelayManagerSnapshot`) — causes the 46s event loop lag measured in health checks

### Fix: Add a scoped relay-only tail reader instead of reading all audit events

**File: `packages/local-store/src/index.ts`**
1. Add a new method `readAuditEventsTail(filter, limit)` that reads the file from the **end** (using a reverse line reader or stat + read last N bytes approach) instead of parsing the entire file. For the snapshot use case, only `relay.*` protocol events are needed, and only the last 12.

**File: `apps/node/src/index.ts`**
2. In `runRelayManagerSnapshotCycle` (line 4522-4523), replace `taskStore.readAuditEvents()` with the new scoped tail reader: `taskStore.readAuditEventsTail({ protocolPrefix: "relay.", limit: 12 })`.

3. Add a startup **audit log size guard** (similar to the existing 32MB guard for `audit-query-index.jsonl` at line 273): if `audit-events.jsonl` exceeds a threshold (e.g. 64MB), truncate or archive it at startup with a warning. This prevents the file from growing unbounded.

**Estimated impact**: Reduces per-cycle cost from O(122MB read + parse) to O(last ~5KB read + parse). Eliminates the 30s periodic CPU spike. Unblocks Allen's mesh initialization.

## Issue 2 (P0): Sponsor Friend Dial Hints Missing Direct LAN Addr

### Root Cause
When Emily sends hello to Allen for auto-bond:
1. `loadBundledSponsorFriendParsed()` only returns `invite.targetMultiaddrs` (circuit-only, because `wan-public` filter strips LAN at invite creation)
2. `invite.bootstrapPeers` (which includes Allen's LAN addr `192.168.3.85:64589`) is NOT extracted
3. `pickAddressFilterForPeer()` sees only circuit addrs → returns `"wan-public"` → strips LAN addr from discovery seeds
4. Emily dials Allen only via cn-relay circuit — which fails with NO_RESERVATION

### Fix: Approach A — Enrich bundled sponsor parsing to include bootstrapPeers

**File: `apps/node/src/bundled-sponsor-friend-loader.ts`**
1. Add `bootstrapPeers: string[]` to `BundledSponsorFriendParsed` type (line 102-108)
2. In `loadBundledSponsorFriendParsed()` (line 137), also return `invite.bootstrapPeers ?? []`
3. In `backfillBundledSponsorPeerAddresses()` (line 168), merge `parsed.bootstrapPeers` into the peer directory alongside `parsed.multiaddrs`

**File: `apps/node/src/node-service-impl.ts`**
4. In `_gatherSponsorMultiaddrs()` (line 2171), merge `parsed.bootstrapPeers` into `fromBundled`:
   ```typescript
   const fromBundled = [...parsed.multiaddrs, ...(parsed.bootstrapPeers ?? [])];
   ```
   This makes `pickAddressFilterForPeer` see the LAN addr → returns `"all"` → LAN addr survives the filter.

**Estimated impact**: Emily will try Allen's direct LAN addr first (both on same Mac), falling back to circuit. Fixes auto-bond for same-LAN sponsor/sponsoree pairs. Also fixes the backfill so the peer directory has the LAN addr for manual dials.
