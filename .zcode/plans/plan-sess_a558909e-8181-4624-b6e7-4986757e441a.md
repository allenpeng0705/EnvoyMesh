# Fix: Inbox badge does not clear after viewing profile-update notifications

## Root cause (confirmed)

The Inbox badge (`useInboxActivityCount`) sums the lengths of six in-memory arrays, including `feedNotifications`. A profile update on Node A fans out a `feed.notify` envelope; Node B persists it and pushes it to the UI, incrementing the badge. The only way to decrement it today is clicking **Dismiss** or **Open in Browser** on each row — both call `dismissFeed(id)`. **Merely opening the Inbox does nothing.** There is no mark-as-read concept and no "clear on open" behavior. Because profile re-publishes generate fresh envelope IDs each time, the badge keeps climbing.

## Chosen fix: clear feed notifications when the Inbox opens

Per your direction — keep it simple: when the Inbox is opened, clear the feed-notification portion of the badge in one action. This is the conventional "open the folder → unread count clears" UX. No schema change, no per-row read state, no new long-lived RPC state.

## Implementation

### 1. Node side — add bulk dismiss (apps/node)

- **`apps/node/src/feed-notify-store.ts`**: add `dismissAllFeedNotifyInboxItems(profileDir)` that empties the JSON list and returns the (empty) next list. Mirrors the existing `dismissFeedNotifyInboxItem` shape.
- **`apps/node/src/node-service-impl.ts`**: add `async dismissAllFeedNotifications(): Promise<void>` next to `dismissFeedNotification` (line 5491); it calls the new store helper.
- **`apps/node/src/json-rpc-router.ts`**: register the `dismissAllFeedNotifications` method (no params), next to the existing `dismissFeedNotification` registration (line 413).
- **`packages/api/src/node-service.ts`**: add `dismissAllFeedNotifications(): Promise<void>` to the `NodeService` interface and `NodeServiceClient` (mirrors `dismissFeedNotification`).

### 2. Social UI side — clear on Inbox open (apps/social)

- **`apps/social/src/hooks/useNodeService.tsx`** (`useFeedNotifications`, line 1958): add a `dismissAll` method that calls `client.dismissAllFeedNotifications()` then `setItems([])`. Return it alongside `items` and `dismiss`.
- **`apps/social/src/components/views/InboxView.tsx`**: pull `dismissAll` from the hook and call it in a `useEffect([])` (mount) so the feed notifications clear — and the badge drops — the moment the Inbox opens. The individual Dismiss/Open-in-Browser buttons remain for in-session use before the user leaves the Inbox. Use a ref guard so the clear only fires once per mount, not on every re-render.
- **`apps/social/src/hooks/useInboxActivityCount.ts`**: no change needed — it already counts `feedNotifications.length`; once the hook's `items` becomes `[]`, the badge reflects it automatically.

### 3. Regression test

- **`apps/social/test/inbox-badge-clear.test.tsx`** (new): jsdom component test that:
  1. Seeds `useFeedNotifications` with 2 items via a fake client.
  2. Renders `InboxView`.
  3. Asserts `dismissAllFeedNotifications` was called on mount.
  4. Asserts the hook's `items` becomes `[]` after mount.
  5. Asserts `useInboxActivityCount` returns the expected value with zero feed notifications (mock the other arrays to 0).

  Follow the existing `apps/social/test/*.test.tsx` patterns (vitest + @testing-library/react + jsdom env comment).

## Why this approach

- **Simplest possible change**: one new bulk RPC + one mount effect. No schema migration, no per-row read flag, no `viewedAt` plumbing through five layers.
- **Matches user expectation**: opening the Inbox clears the badge, exactly like email/messaging apps.
- **Preserves the existing Dismiss buttons**: in-session, before leaving the Inbox, users can still dismiss individual items.
- **No persistence ambiguity**: feed notifications are inherently ephemeral activity pings (article/photo/profile publishes). Clearing them on view is the right semantic — they are not actionable requests like approvals or share offers, which keep their own accept/decline flows and are NOT auto-cleared.

## Out of scope (intentionally)

- Pending approvals, share offers, intro proposals, hellos, stranger messages — these are **actionable requests** with explicit accept/decline flows and must NOT be auto-cleared on Inbox open. Only the ephemeral `feedNotifications` array is cleared.
- Mobile (`packages/mobile-node`) — per your scope choice, desktop only. The mobile `dismissFeedNotification` no-op is noted but not changed in this pass.
- Per-notification read/viewed state — not needed for the "clear on open" UX. Can be added later if you want "view without dismissing."
